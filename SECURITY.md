# Модель безопасности RanobeSite

Фронтенд — статический сайт. Всё, что в нём выполняется, может прочитать и подменить пользователь. Поэтому **все проверки прав выполняются в базе данных**: политики Row Level Security, права на столбцы и функции `SECURITY DEFINER`. Проверки в React нужны только для удобства (спрятать кнопку, перенаправить на вход) и защитой не являются.

## Ключи

| Ключ | Где | Почему так |
| --- | --- | --- |
| Project URL, `anon` / publishable key | `.env.local`, переменные CI, JS в браузере | Публичные по задумке Supabase. Дают только права ролей `anon` и `authenticated`, ограниченные RLS. |
| `service_role` / secret key | Нигде в проекте | Обходит RLS. Если он попадёт в `VITE_SUPABASE_ANON_KEY`, приложение откажется запускаться (`src/lib/env.ts`). |

`.env*` (кроме `.env.example`) исключены из Git. Тестовых аккаунтов и паролей в репозитории нет: тесты базы создают пользователей во временной базе в памяти.

## Роли

- **Гость (`anon`)** — не вошёл в аккаунт.
- **Читатель** — любой зарегистрированный участник, роль `reader` выдаётся при регистрации.
- **Модератор** — проверяет заявки и жалобы.
- **Администратор** — всё, что модератор, плюс приглашения, роли и настройки доступа.

Роли хранятся в `user_roles`. У клиентских ролей нет прав `INSERT`, `UPDATE` и `DELETE` на эту таблицу. Изменить роль можно только функцией `set_user_role()`, которая проверяет, что вызывающий — администратор. Снять роль администратора с самого себя нельзя, чтобы не потерять управление.

## Закрытый режим и будущее открытие

Таблица `app_settings` (одна строка) хранит:

- `registration_mode`: `invite` (сейчас) или `open`;
- `catalog_access`: `members` (сейчас) или `public`.

Функция `can_read_catalog()` возвращает `true`, если пользователь вошёл или каталог открыт. Её используют политики чтения книг, глав, жанров, профилей, отзывов, комментариев и файлов. Поэтому открытие каталога сводится к смене одного значения: политики переписывать не нужно, а черновики и личные данные остаются закрытыми в любом режиме.

Менять настройки может только администратор через `update_app_settings()`. Прямого доступа к таблице нет ни у кого из клиентов. Фронтенд узнаёт режим через `get_public_config()`, которая возвращает только эти два поля.

## Регистрация по приглашениям

- `invites`: код (64 бита случайности при генерации), роль для нового участника, лимит использований, срок действия, необязательная привязка к e-mail, отметка об отзыве.
- Триггер `handle_new_user` на `auth.users` в одной транзакции:
  1. проверяет приглашение (блокируя строку `FOR UPDATE`, чтобы два человека не использовали одноразовый код одновременно);
  2. создаёт профиль и роль;
  3. увеличивает счётчик использований.

  При недействительном приглашении триггер выбрасывает исключение, и Supabase Auth не создаёт пользователя. Обойти это из браузера нельзя.
- `check_signup()` даёт фронтенду заранее показать понятную ошибку. Свободно ли имя пользователя, она сообщает только при действующем приглашении, чтобы посторонние не перебирали имена участников.
- Список приглашений видят только администраторы.

## Политики по таблицам

| Таблица | Чтение | Запись клиентом |
| --- | --- | --- |
| `profiles` | `can_read_catalog()` | своя строка: `username`, `display_name`, `bio`, `avatar_path` |
| `user_roles` | `can_read_catalog()` (значки «Модератор») | нет |
| `books` | опубликованные при `can_read_catalog()`; свои; модераторы — все | создание своих (только содержательные поля); правка своих черновиков и отклонённых; удаление своих никогда не публиковавшихся |
| `book_genres` | вместе с видимой книгой | нет (`set_book_genres()`, только для черновиков) |
| `book_revisions` | автор, модераторы | автор: правка и удаление своих в состояниях `draft` / `rejected` |
| `chapters` | опубликованные главы опубликованных книг; автор; модераторы | автор: номер главы; удаление неопубликованной |
| `chapter_revisions` | автор; модераторы; читатели — **только текущая опубликованная версия** | автор: заголовок и текст в `draft` / `rejected` |
| `moderation_queue`, `moderation_events` | автор — свои заявки, модераторы — все | нет (только функции) |
| `library_entries`, `reading_progress` | только владелец | только владелец |
| `reviews` | вместе с видимой книгой | своя оценка опубликованной **чужой** книги |
| `comments` | вместе с видимой книгой | свои; удаление — автор или модератор |
| `notifications` | только получатель | отметка «прочитано», удаление |
| `reports` | автор жалобы, модераторы | создание своей |
| `invites`, `invite_uses` | администраторы | нет (только функции) |
| `app_settings` | нет | нет (только функции) |

### Защищённые поля

Права на запись выдаются **по столбцам**. У клиента физически нет права изменить:

- `publication_state`, `published_at`, `rejection_reason`;
- счётчики: `chapters_count`, `rating_avg`, `library_count`;
- `published_revision_id`;
- статусы заявок;
- `author_id` и `slug`.

Запрос вида `update books set publication_state = 'published'` завершается ошибкой `permission denied`, даже если политика RLS разрешила бы строку. Это покрыто тестами.

## Публикация и модерация

Все переходы состояний выполняют функции `SECURITY DEFINER`:

- **автор:** `submit_book`, `submit_book_revision`, `submit_chapter_revision`, `start_book_revision`, `start_chapter_revision`, `create_chapter`, `set_book_genres`, `set_book_status`, `cancel_submission`;
- **модератор:** `approve_submission`, `reject_submission`, `set_book_hidden`, `resolve_report`.

Каждая функция:

- объявлена с `SET search_path = ''`, все имена в ней полные (`public.books`, `auth.uid()`), поэтому подмена объектов через `search_path` невозможна;
- сама проверяет права (`require_user()`, `assert_book_author()`, `is_staff()`, `is_admin()`);
- выполняется от владельца, но права на её вызов есть только у нужной роли. Миграция сначала отзывает `EXECUTE` у `PUBLIC`, `anon` и `authenticated` на все функции, а затем выдаёт права точечно. Служебные функции (`notify_user`, `refresh_book_stats`, `lock_pending_submission` и т. п.) клиенту недоступны.

**Атомарность.** Одобрение — одна транзакция: блокируется заявка (`FOR UPDATE`), проверяется статус `pending`, меняется опубликованная версия или книга, пишется журнал, создаётся уведомление. Если что-то упадёт, не изменится ничего.

**Повторная обработка.** Повторное одобрение или отклонение обработанной заявки возвращает ошибку «Заявка уже обработана». Частичные уникальные индексы не дают создать две активные заявки на один объект.

**Самоодобрение.** Автор без роли модератора не может вызвать функции модерации. Модератор не может обработать собственную заявку. Администратор может: на небольшом закрытом сайте он часто и автор.

**Версии глав.** Читатели видят версию, на которую указывает `chapters.published_revision_id`. Правка создаёт новую версию. Пока её не одобрят, читатели продолжают видеть прежний текст. После одобрения старая версия помечается `superseded` и перестаёт быть видимой читателям.

**Обязательная причина отказа.** `reject_submission` требует причину не короче 5 символов.

## Хранилище файлов

- Бакет `media` **приватный**: изображения выдаются по подписанным ссылкам на час и только тем, кому доступен каталог.
- Лимит в бакете — 5 МБ, MIME-типы — только JPEG, PNG и WebP.
- Загрузка возможна только в свою папку (`covers/<user_id>/…`, `avatars/<user_id>/…`) и только с расширениями изображений. Изменять и удалять можно только файлы в своей папке.
- На клиенте тип и размер проверяются заранее, а изображение уменьшается и перекодируется в WebP.

## Защита от XSS

- Текст глав хранится как JSON-документ Tiptap, а не как HTML. Ограничение в базе: корень документа — `doc`, размер — не больше 600 КБ.
- Компонент `RichText` превращает документ в React-элементы по белому списку узлов и меток:
  - неизвестные узлы (`iframe`, `image` и любые другие) отбрасываются, остаётся только их текст;
  - `<script>` внутри текста выводится как обычный текст;
  - ссылки разрешены только `http(s):` и `mailto:`, с `rel="noopener noreferrer nofollow ugc"`.
- `dangerouslySetInnerHTML` в проекте не используется. Комментарии, отзывы, описания и профили выводятся как обычный текст, React экранирует их автоматически.
- Ссылки в уведомлениях ограничены внутренними путями: проверка в базе и при выводе.

## Ограничение частоты

Пока сайт закрыт, защита от спама намеренно простая. Число одновременных заявок одного автора ограничено (`app_settings.max_pending_submissions`, по умолчанию 30). Supabase Auth сам ограничивает частоту входов и писем. Прогресс чтения отправляется на сервер не чаще раза в 8 секунд и при уходе со страницы.

## Проверка

`npm run test:db` применяет миграции к PostgreSQL (PGlite) и выполняет запросы от ролей `anon` и `authenticated`. Проверяется:

- регистрация без приглашения, с исчерпанным, отозванным и просроченным приглашением, с чужим e-mail;
- невозможность выдать себе роль или изменить служебные поля;
- закрытый каталог для гостей и его открытие переключателем;
- полный цикл модерации, защита от повторной обработки и самоодобрения;
- видимость версий глав;
- изоляция библиотеки и прогресса;
- правила хранилища.

## Чек-лист перед открытием сайта

1. Подключить свой SMTP и включить подтверждение e-mail.
2. Включить CAPTCHA в Supabase Auth (Attack Protection) и настроить лимиты частоты.
3. Пересмотреть `max_pending_submissions` и при необходимости добавить ограничения частоты для комментариев и отзывов (сейчас их нет).
4. Убедиться, что в **Authentication → URL Configuration** указаны только ваши домены.
5. Проверить, что у модераторов есть время разбирать очередь и жалобы.
6. Включить переключатели в **Администрировании → Доступ к сайту**.
