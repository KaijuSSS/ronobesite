# ЗАДАНИЕ ДЛЯ AI-АГЕНТА: Создать сайт для чтения ранобэ и книг

Ты — опытный Senior Full-Stack Developer, UI/UX Designer и специалист по безопасности веб-приложений.

Твоя задача — **создать полноценный, современный и работоспособный сайт для чтения и публикации текстовых книг, ранобэ, веб-новелл и рассказов**, похожий по функциональности на RanobeLib, Remanga и Senkuro, но с собственным оригинальным дизайном.

**Название проекта:** RanobeSite (временно).

**Важно:** Не ограничивайся созданием макета или описанием архитектуры. Пиши реальный рабочий код, создавай необходимые файлы и папки, устанавливай зависимости, исправляй ошибки, проверяй сборку и доведи приложение до работоспособного состояния.

## 1. Технологический стек

Используй:

- React + TypeScript
- Vite
- Tailwind CSS
- shadcn/ui
- Lucide React для иконок
- React Router
- TanStack Query
- Zustand
- Supabase PostgreSQL
- Supabase Auth
- Supabase Storage
- Tiptap для редактирования глав
- GitHub Pages для размещения фронтенда

Не используй Next.js, Express или сервер Node.js для основного приложения, поскольку фронтенд должен работать на GitHub Pages.

Допускается использование Supabase Edge Functions и защищённых PostgreSQL-функций для серверных операций.

Используй актуальные совместимые версии библиотек и проверь документацию перед настройкой.

## 2. Дизайн сайта

Создай привлекательный интерфейс в стиле современных сайтов с ранобэ.

Основные требования:

- Тёмная тема по умолчанию.
- Фон тёмно-серый, близкий к `#101115`.
- Карточки немного светлее основного фона.
- Акцентные цвета: фиолетовый и синий.
- Красивые скругления, мягкие тени.
- Современная типографика.
- Плавные переходы и анимации.
- Скелетоны во время загрузки.
- Адаптивность для телефонов, планшетов и компьютеров.
- Верхняя навигационная панель на компьютерах.
- Удобная мобильная навигация.
- Красивые состояния пустых страниц и ошибок.

Дизайн должен быть оригинальным. Не копируй изображения, логотипы, CSS и фирменные элементы существующих сервисов.

Весь пользовательский интерфейс должен быть на русском языке.

## 4. Студия автора

Создай защищённый раздел `/studio`.

Каждый зарегистрированный пользователь может создавать произведения и главы, но **публикация доступна только после одобрения модератором**.

Функции:

- Создание произведения.
- Редактирование названия и описания.
- Загрузка обложки.
- Выбор жанров.
- Сохранение черновика.
- Просмотр своих произведений.
- Добавление глав.
- Редактирование текста через Tiptap.
- Предварительный просмотр главы.
- Отправка книги или главы на модерацию.
- Просмотр статуса проверки.
- Отображение причины отказа.
- Повторная отправка исправленной версии.

При редактировании опубликованной главы прежняя опубликованная версия должна оставаться доступной читателям до одобрения новой.

Реализуй автоматическое сохранение черновиков с debounce.

Создай раздел `/moderation`, доступный только модераторам и администраторам.

Реализуй:

- Список ожидающих проверки произведений.
- Список ожидающих проверки глав.
- Просмотр полного содержимого заявки.
- Просмотр автора заявки.
- Кнопку одобрения.
- Кнопку отклонения.
- Обязательное указание причины отклонения.
- Историю проверок.
- Фильтры по статусу.
- Защиту от повторной обработки одной заявки.

Одобрение должно атомарно изменять состояние заявки и соответствующей публикации.

Не допускай, чтобы обычные пользователи могли одобрять собственные книги, меняя запросы из браузера.

## 6. Структура базы данных

Подготовь SQL-миграции в папке `supabase/migrations`.

Основные таблицы:

1. `profiles` — публичные данные пользователей.
2. `user_roles` — роли reader, moderator, admin.
3. `books` — произведения и их состояние публикации.
4. `book_revisions` — предложенные изменения опубликованных произведений.
5. `genres` — жанры.
6. `book_genres` — связь произведений с жанрами.
7. `chapters` — главы.
8. `chapter_revisions` — черновики, заявки и опубликованные версии.
9. `moderation_queue` — очередь проверок.
10. `moderation_events` — журнал модерации.
11. `library_entries` — библиотека пользователей.
12. `reading_progress` — прогресс чтения.
13. `reviews` — отзывы и оценки.
14. `comments` — комментарии.
15. `notifications` — уведомления.
16. `reports` — жалобы.

Используй UUID, внешние ключи, уникальные ограничения, индексы и корректные значения по умолчанию.

Продумай каскадное удаление, чтобы пользователь случайно не мог удалить чужой контент.

Создай механизм автоматического создания профиля после регистрации.

Для опубликованных глав используй указатель `published_revision_id` на одобренную версию.

## 7. Безопасность Supabase

Это критически важная часть.

Обязательно:

- Включи Row Level Security на всех публично доступных таблицах.
- Читатели могут просматривать только опубликованные книги и версии глав.
- Авторы могут изменять только свои черновики и заявки.
- Модераторы могут просматривать и обрабатывать заявки в рамках своих полномочий.
- Пользователь не может сам выдать себе роль администратора.
- Приватные данные пользователей не должны раскрываться через публичные запросы.
- Запрети изменение защищённых полей через прямые запросы клиента.
- Защити SQL-функции с `SECURITY DEFINER`, ограничь доступ и настрой безопасный `search_path`.
- Не раскрывай ключ `service_role` в клиентском приложении.
- Проверяй размер, тип и права доступа загружаемых файлов.
- Предусмотри ограничения на частоту публикации контента.
- Защити отображаемый текст от XSS.

Проверяй права не только в React, но и непосредственно на уровне базы данных.

Создай SQL-миграцию с RLS-политиками и отдельный документ `SECURITY.md`, объясняющий модель доступа.

## 9. GitHub Pages

Сайт должен собираться командой:

`npm run build`

И запускаться локально командой:

`npm run dev`

Настрой Vite для публикации в подпапке репозитория GitHub.

Используй `import.meta.env.BASE_URL` там, где это необходимо.

Выбери подходящий способ роутинга для GitHub Pages. Для первой версии допустим `HashRouter`, чтобы прямое открытие страниц не приводило к ошибке 404.

Создай `.github/workflows/deploy.yml` для автоматической публикации после отправки изменений в основную ветку.

Никакие серверные секреты не должны попадать в workflow, фронтенд или Git-репозиторий.
